## 1. `.env` 跟踪历史与敏感配置清理方案

### 背景

检查发现 `apps/admin/.env.production` 被 git 跟踪（历史遗留）。该文件包含生产环境配置，不应纳入版本管理。

当前状态：

```
apps/admin/.env.production        → 已跟踪（历史遗留，v0.2.4 已标记）
apps/backend/.env.example          → 已跟踪（示例文件，正常）
apps/backend/.env                  → 未跟踪（正常）
```

### 设计方案

| 步骤 | 内容 | 是否需要代码修改 |
|------|------|:--------------:|
| 1.1 | 只读审计：确认 `.env.production` 中是否含敏感信息（token、secret、API key） | ❌ 否，只读检查 |
| 1.2 | 设计清理方案：a) `git rm --cached` 停止跟踪；b) 补充 `.gitignore` 规则；c) 创建 `.env.example` 替换 | ✅ 是 |
| 1.3 | 创建迁移说明文档，确保不影响线上部署 | ❌ 否，仅文档 |
| 1.4 | 实施清理：执行 `git rm --cached` + 更新 `.gitignore` + 提交 | ✅ 是 |

### 风险

- `git rm --cached` 后会从 git 删除，但不影响本地文件，不影响 PM2/Nginx 部署
- 需要同步更新 `.gitignore` 防止重新提交
- 如果该文件实际被 CI/CD 或部署脚本引用，需评估替代路径

### 产出

```
docs/architecture/v0.2.5-env-cleanup-design.md
→ 清理脚本 / .gitignore 更新 / 文档更新（经用户确认后执行）
```

## 2. 日志规范化代码实施方案

### 背景

v0.2.4 已完成日志规范化的**只读评估**（`docs/openclaw-reports/` 下有评估报告）。当前生产环境仍以 `console.log` / `console.error` 原始输出，PM2 日志无结构化格式，无日志级别区分。

推荐阅读：`docs/openclaw-reports/v0.2.4-logging-normalization-assessment.md`

### 设计方案

| 步骤 | 内容 | 是否需要代码修改 |
|------|------|:--------------:|
| 2.1 | 选择日志方案：NestJS 内置 Logger vs winston vs pino（评估报告已有结论） | ❌ 否，仅文档 |
| 2.2 | 创建 Logger 全局模块：`common/logger/logger.module.ts` + `logger.service.ts` | ✅ 是 |
| 2.3 | 替换后端所有 `.controller.ts` / `.service.ts` 中的 `console.log` / `console.error` | ✅ 是 |
| 2.4 | 请求级 LoggingInterceptor 注册（含 requestId、userId、path、耗时） | ✅ 是 |
| 2.5 | 配置 PM2 日志格式，确保结构化日志可被 journal/ELK 消费 | ❌ 否，仅配置 |

### 风险

- 直接替换 `console.log` 可能影响线上调试习惯
- 建议分批次替换：先替换高频 Service（OrderService、TaskService），再替换 Controller
- 替换后验证 PM2 error.log / out.log 格式无异常

### 产出

```
docs/architecture/v0.2.5-logging-implementation-design.md
→ 具体替换清单 / 影响范围评估（经用户确认后执行）
```

## 4. 任务治理只读增强方案

### 背景

Admin controller 已有治理动作端点以及只读查询。前端任务管理页面（`tasks/index.vue`）和订单管理页面（`orders/index.vue`）已实现。

用户治理在 v0.2.0～v0.2.2 阶段已完成：用户 CRUD、重置密码、角色调整、封禁/解封。
任务/订单治理目前仅支持强制操作，缺少**前端可判断的权限/操作可见性信息**。

### 设计方案

| 步骤 | 内容 | 是否需要代码修改 |
|------|------|:--------------:|
| 4.1 | 只读巡检：检查任务列表 API 是否含 `forceCancelAllowed` 等前端判断字段 | ❌ 否，只读 |
| 4.2 | 只读巡检：检查订单列表 API 是否含 `forceCompleteAllowed` / `forceRejectAllowed` | ❌ 否，只读 |
| 4.3 | 只读巡检：确认 audit log 的 `detailJson` 是否被前端正确展示 | ❌ 否，只读 |
| 4.4 | 设计增强方案：API 新增操作可见性字段 + 前端按钮联动 | ❌ 否，仅设计文档 |
| 4.5 | 实施 API 增强（仅添加字段，不修改业务逻辑） | ✅ 是 |
| 4.6 | 前端联动（仅按钮显隐，不修改状态机） | ✅ 是 |

### 风险

- 极低。API 新增字段不破坏现有格式，前端显隐不触发状态变更
- 不改 status 字段，不改 Wallet/LedgerEntry
- 不改任务/订单状态机

### 产出

```
docs/architecture/v0.2.5-task-governance-enhancement-design.md
→ API 字段 / 前端联动 / 权限矩阵设计（经用户确认后执行）
```

## 5. 管理后台登录失败/限流/fail2ban 方案

### 背景

当前管理后台 `admin.haoyulv.com` 登录无失败次数限制，无 IP 级限流，无 fail2ban 保护。暴力破解风险存在。

### 设计方案

| 步骤 | 内容 | 是否需要代码修改 |
|------|------|:--------------:|
| 5.1 | 设计后端登录失败次数守卫：基于内存/Redis 记录 IP + email 失败次数 | ❌ 否，仅设计 |
| 5.2 | 实施后端守卫：NestJS 自定义 Guard + 限制策略（5 次/30min → 临时禁止） | ✅ 是 |
| 5.3 | 设计 Docker nginx 级别限流：`limit_req_zone` + `limit_conn_zone` | ❌ 否，仅设计 |
| 5.4 | 实施 nginx 限流：添加 `admin.haoyulv.com.conf` 的 limit_req 规则 | ✅ 是（仅配置文件） |
| 5.5 | 设计 fail2ban 规则：监控 Docker nginx 日志，封禁异常 IP | ❌ 否，仅设计 |
| 5.6 | 实施 fail2ban：host 级别安装 fail2ban + Docker 日志适配 | ✅ 是（仅系统配置） |
| 5.7 | 验证：多次错误登录 → 触发限流 → 恢复正常 | ❌ 否，手动验证 |

### 方案对比

| 方案 | 复杂度 | 效果 | 运维成本 |
|------|--------|------|---------|
| A. 仅后端 Guard | 低 | 阻止暴力登录，但 IP 仍可持续请求 | 低 |
| B. 后端 Guard + nginx limit_req | 中 | IP 级请求限速 + 登录失败封禁 | 中 |
| C. 后端 Guard + nginx + fail2ban | 高 | 完整三层防御（应用/网络/系统） | 中高 |

**建议选择 B 作为 v0.2.5 目标**，C 作为后续补充。

### 风险

- 后端 Guard 不影响已有登录逻辑，仅校验失败次数
- nginx limit_req 配置需确认不与 Cloudflare 代理模式冲突（CF 出口 IP 固定）
- fail2ban 为系统级配置，不修改代码/db

### 产出

```
docs/architecture/v0.2.5-admin-login-rate-limit-design.md
→ 三层防御架构设计 / nginx 配置示例 / fail2ban 规则 / 验证方案
```
