## 2. 后端 req.ip 实际值是否为真实客户端 IP

**✅ 后端限流不依赖 `req.ip`，依赖 `x-real-ip`。**

### 实际 IP 追溯链路

```
用户浏览器
  ↓ CF-Connecting-IP: 203.0.113.1
Cloudflare 边缘
  ↓ CF-Connecting-IP: 203.0.113.1
Nginx (Docker)
  ↓ proxy_set_header X-Real-IP $login_limit_key
  ↓ $login_limit_key = $http_cf_connecting_ip = "203.0.113.1"
后端 LoginThrottleGuard
  ↓ getClientIp(): req.headers['x-real-ip'] = "203.0.113.1"  ✅
  ↓ clearIp(): req.headers['x-real-ip'] = "203.0.113.1"     ✅
```

### 验证方式

```typescript
// login-throttle.guard.ts - getClientIp
private getClientIp(request: Request): string {
  return (
    (request.headers['x-real-ip'] as string) ||       // ← 优先使用 Nginx 设置的头
    (request.headers['x-forwarded-for'] as string) ||
    request.ip ||                                        // ← 仅做 fallback（127.0.0.1）
    'unknown'
  );
}
```

**结论**: `x-real-ip` 头优先级最高，Nginx 已设置为 `$login_limit_key`（即 CF-Connecting-IP），backend 正确获取。

## 3. X-Real-IP / X-Forwarded-For 是否正确透传

**✅ 正确透传。**

### 当前配置

```nginx

proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

```bash
  → Nginx fallback: $login_limit_key = $binary_remote_addr = x.x.x.x
```

## 5. Nginx limit_req 与后端 LoginThrottleGuard 是否叠加合理

**✅ 叠加合理，两层工作正常。**

### 请求流

```
请求 → Nginx limit_req (30r/m, burst=5)
  ├─ ❌ burst 耗尽 → 返回 HTTP 429 HTML（不向后端转发）
  └─ ✅ burst 未耗尽 → 透传 → 后端 LoginThrottleGuard
       ├─ ❌ IP 超限 (10/15min) → 返回 JSON 429
       ├─ ❌ Email 超限 (5/15min) → 返回 JSON 429
       ├─ ❌ 密码错误 → 返回 JSON 401
       └─ ✅ 密码正确 → 200 + tokens + clearIp + clearEmailFails
```

### 测试验证

```bash
10 次快速请求同一 CF-Connecting-IP (burst=5):
401 401 401 401 401 429 429 429 429 429
  ↑ burst 内, 到达后端      ↑ Nginx 429, 未到达后端
```

**关键**: Nginx 429 后的请求**不消耗后端任何资源**，后端 Email 失败计数不变。

## 7. 错误登录先触发 Nginx 429 还是后端 429

**取决于攻击速率。**

| 攻击场景 | 先触发 |
|---------|-------|
| **慢速暴力破解**（< 30 次/分） | **后端** → 5 次 email 失败 / 10 次 IP 失败 → JSON 429 |
| **快速自动化**（> 30 次/分） | **Nginx** → burst 耗尽 → HTML 429（后端不受影响） |

### 时序

```
慢速 (< 30r/m):  backend backend backend backend backend (429)
                 ↑ 后端 email 限制 5 次先到达

快速 (> 30r/m):  Nginx  Nginx  Nginx  Nginx  Nginx (429)
                 ↑ Nginx burst 耗尽先到达
                 ↑ 后端计数不受影响
```

**结论**: 慢速暴力由后端精确处理（含 email 级隔离），快速暴力由 Nginx 兜底拦截（后端资源零消耗）。

## 8. 是否存在双层 429 message 不一致问题

**⚠️ 存在。Nginx 429 返回 HTML，后端 429 返回 JSON。**

### 双层响应对比

| 层 | 状态码 | Content-Type | Body |
|---|:------:|:------------:|------|
| **Nginx** `limit_req` | 429 | `text/html` | `<html>...429 Too Many Requests...</html>` |
| **后端** `LoginThrottleGuard` | 429 | `application/json` | `{"statusCode":429,"error":"HttpException",...}` |

### 影响分析

| 场景 | 前端行为 | 风险 |
|------|---------|:----:|
| 前端 fetch 正常 | `response.ok = false`, `response.status = 429` | 🟢 低 — fetch 不关心 body |
| 前端 `response.json()` | 解析 HTML 会抛错 | 🟡 中 — 需 try/catch |
| 前端 `error.response?.data?.message` | HTML body 无 `message` 字段 | 🟡 中 — 需 fallback |

### 建议修复

**在 Nginx 中配置自定义 429 JSON 响应**（Nginx phase 补充）：

```nginx
# 方案一：在 http 块中定义
error_page 429 /429.json;
location = /429.json {
    internal;
    default_type application/json;
    return 429 '{"statusCode":429,"error":"TooManyRequests","message":"登录请求过于频繁，请稍后再试","path":"/api/auth/login","timestamp":"$time_iso8601"}';
}

# 方案二：直接在 location 中使用 return
error_page 429 @return429;
location @return429 {
    default_type application/json;
    return 429 '{"statusCode":429,"error":"TooManyRequests","message":"登录请求过于频繁，请稍后再试"}';
}
```

**风险**: 🟢 低。不影响后端逻辑，仅改变 Nginx 429 响应格式。
