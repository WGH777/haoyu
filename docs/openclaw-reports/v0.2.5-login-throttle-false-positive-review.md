## 1. IP 维度是否统计成功登录请求

**✅ 确认：IP 计数器统计所有登录请求（含成功）。**

```typescript
// login-throttle.guard.ts, canActivate() 入口处
// 每次请求到达此方法，无论后续登录成功还是失败，IP 计数都会 +1
let ipRec = ipRequestMap.get(ip);
if (!ipRec || now - ipRec.windowStart >= IP_WINDOW_MS) {
  ipRec = { count: 1, windowStart: now };
} else {
  ipRec.count++;  // ← 每次请求都增加，不区分成功/失败
  if (ipRec.count > IP_MAX_REQUESTS) {
    throw new HttpException(...); // 429
  }
}
```

**影响**: 成功登录也消耗 IP 限额。一个用户频繁登录/登出 10 次后会触发 IP 级 429。

| 场景 | IP 限额耗尽时间 | 触发 429 |
|------|:--------------:|:-------:|
| 用户正常输入密码 1~2 次后成功 | ✅ 不可能耗尽 | ❌ |
| 用户连续测试 10 次密码（含正确） | 15 分钟内 ⚠️ | ✅ |
| 同一个 VPN/School IP 下 10 人各登录 1 次 | 15 分钟内 ⚠️ | ✅ |
| 用户正常每天登录 2~3 次 | 不可能耗尽 | ❌ |

**结论**: 当前行为正确但有优化空间。成功登录后应清除 IP 计数（见第 3 点）。

## 2. 成功登录后是否清除 email 失败记录

**✅ 确认：成功登录后清除 email 失败记录。**

```typescript
// auth.controller.ts
const result = await this.authService.signIn(dto.email, dto.password);
LoginThrottleGuard.clearEmailFails(dto.email);  // ← 成功时清除
return result;
```

清除路径：

```
用户登录成功
  → authService.signIn() 返回 tokens
  → LoginThrottleGuard.clearEmailFails(email)  // emailFailMap.delete(email)
  → 返回 200
```

**验证方式**: 连续 5 次密码错误后同 email 触发 429 → 用正确密码登录成功 → email 限制归零，可再次尝试。

**结论**: 正确实现，无需修正。

## 3. 成功登录后是否需要清除 IP 记录

**⚠️ 当前未清除，建议在本阶段补上。**

### 现状

`LoginThrottleGuard` 提供 `clearIp()` 静态方法（已存在），但在 `auth.controller.ts` 的成功分支中**未被调用**。

```typescript
// 已存在但未调用
static clearIp(ip: string): void {
  ipRequestMap.delete(ip);
}
```

### 建议：在 controller 的成功分支中调用 clearIp

在 `auth.controller.ts` 中补充：

```typescript
const result = await this.authService.signIn(dto.email, dto.password);
LoginThrottleGuard.clearEmailFails(dto.email);
LoginThrottleGuard.clearIp(req.ip);  // ← 新增：清除 IP 计数
return result;
```

### 影响分析

| 维度 | 不清理 IP | 清理 IP（建议） |
|------|----------|---------------|
| 用户频繁登出/登入 | 10 次后触发 429 | 每次都正常 |
| VPN 共享 IP | 10 人各成功登录 1 次，第 11 人 429 | 每人成功登录后 IP 重置 |
| 暴力攻击 | 攻击者 IP 成功登录后需重新计数 | ✅ 同样重置（攻击者可能仅获取一个账号） |
| 安全性影响 | 更严格 | 略宽松，但 15 分钟 10 次仍然合理 |

**建议**: 在本阶段（P0-4 同一 commit 前）补充 `clearIp()` 调用，不等 Nginx phase。因为：
- 代码修改极小（+1 行）
- 显著降低误伤
- clearIp() 方法已存在，唯一缺的是调用
- 即使攻击者成功登录，IP 重置后仍需破解下一个密码（而不是无限尝试）

## 4. 同一 IP 多账号正常登录是否可能 15 分钟内误触发 429

**⚠️ 可能，风险等级：中等。**

### 风险场景

| 场景 | 详细 | 误伤概率 |
|------|------|:-------:|
| 家庭宽带 NAT 出口 | 家庭 3~5 人，每人登录 2~3 次/天 | **低** (< 10 次) |
| 办公室/VPN 共享 IP | 10+ 人，每人登录 1~2 次/天 | **中** (可能触及 10 次) |
| 公司代理统一出口 | 50+ 员工，每人登录 1 次/天 | **高** (5 分钟内已超限) |
| 云服务商 NAT | 同一 IP 段多人使用 | **高** |

### 缓解措施（按等级）

| 缓解 | 效果 | 实施成本 | 建议阶段 |
|------|------|---------|---------|
| ✅ 成功登录后 `clearIp()` | 显著降低误伤 | 低（+1 行代码） | **本阶段** |
| Nginx `limit_req` 使用 `$http_cf_connecting_ip` | 区分 CF 真实 IP，减少 NAT 误伤 | 低 | Nginx phase |
| 提高 IP limit（10→20） | 降低密度敏感度 | 极低（改常量） | 备选 |
| 移除 IP 限制，仅保留 email 限制 | 彻底消除误伤 | 极低（删除 IP 检查） | **不推荐**（失去一层防御） |

**结论**: 建议实施 `clearIp()` 后，风险降至低。办公室/VPN 场景仍可能在极端情况下触发，但 15 分钟窗口的自然过期机制可自愈。

## 5. 当前 429 message 是否不泄露账号存在性

**✅ 确认：不泄露。返回值完全一致。**

无论是由 IP 限流触发还是 email 限流触发，均返回：

```json
{
  "statusCode": 429,
  "error": "HttpException",
  "message": "登录请求过于频繁，请稍后再试",
  "path": "/api/auth/login",
  "timestamp": "2026-06-05T..."
}
```

### 和 NestJS 默认 401 的对比

| 状态码 | 触发条件 | 消息 |
|:----:|---------|------|
| 401 | 密码错误 / 用户不存在 / 账号封禁 | `账号或密码错误` |
| 429 | IP 请求超限 / Email 失败超限 | `登录请求过于频繁，请稍后再试` |

- 401 不区分"用户不存在"和"密码错误"（已防御枚举）
- 429 不区分"IP 限流"和"Email 限流"（已防御存在性探测）
- 两者 message 不暴露任何邮箱存在信息 ✅

## 7. 是否建议在本阶段修正 clearIp，还是等 Nginx phase

**✅ 建议在本阶段立即修正。**

### 理由

| 维度 | 本阶段修正 | 等 Nginx phase |
|------|:---------:|:-------------:|
| 改动量 | +1 行代码（`LoginThrottleGuard.clearIp(req.ip)`） | 同上 |
| 风险 | 极低（clearIp 方法已存在，仅新增调用） | — |
| 误伤影响 | 立即降低共享 IP 场景误伤 | 用户持续被 429 |
| Nginx phase 前置 | 无依赖 | 仍需要此修正 |
| 独立回滚 | 可单独 revert | 仍可单独 revert |

### 建议方案

```typescript
// 在 auth.controller.ts 成功分支中增加
const result = await this.authService.signIn(dto.email, dto.password);
LoginThrottleGuard.clearEmailFails(dto.email);
LoginThrottleGuard.clearIp(req.ip);  // ← 新增
return result;
```

**注意**: `req.ip` 已在 Guard 内部通过 `this.getClientIp(request)` 获取，但在 controller 中需要从 `@Req() req` 获取。建议的做法是：

**方案 A**: 在 controller 中用 `req.headers['x-real-ip'] || req.ip` 获取 IP，传给 `clearIp()`

**方案 B**: 让 `clearIp` 不带参数，从当前请求上下文中获取 IP——但 guard 的静态方法无法拿到当前请求

**推荐方案 A**:

```typescript
async signIn(@Req() req: any, @Body() dto: LoginDto) {
  // ...
  const result = await this.authService.signIn(dto.email, dto.password);
  LoginThrottleGuard.clearEmailFails(dto.email);
  // 获取客户端 IP 并清除 IP 计数
  const ip = req.headers['x-real-ip'] || req.ip || 'unknown';
  LoginThrottleGuard.clearIp(ip);
  return result;
}
```

## 8. 是否建议进入 Nginx limit_req 设计复核

**✅ 建议进入 Nginx phase 设计复核，但无需更改当前后端 design doc。**

### 建议复核的 3 个要点

| # | 复核点 | 当前状态 | 建议 |
|---|--------|---------|------|
| 1 | `limit_req` 限流 key | 设计为 `$http_cf_connecting_ip`（CF 代理模式） | 需确认 `$http_cf_connecting_ip` 在 CF 全代理模式下始终存在；需要 fallback 到 `$remote_addr` |
| 2 | Nginx IP 限流与后端 IP 限流的关系 | 后端 10 次/15min；Nginx 设计为 30r/m burst=5 | 需要确保 Nginx 层比后端层宽松，避免 Nginx 429 后用户不知道后端限流已触发 |
| 3 | Nginx 429 响应格式 | 默认返回 Nginx 标准 429 页面（HTML） | 建议返回 JSON 格式与后端保持一致的 `{statusCode: 429, ...}` |

### Nginx phase 入口条件

- [x] 后端 LoginThrottleGuard 已验证通过
- [x] IP + email 双维度限流生效
- [x] 429 结构兼容 HttpExceptionFilter
- [x] `clearIp()` 本阶段修正后，后端保护层就绪
- [ ] Nginx limit_req 配置模板准备
- [ ] CF-Connecting-IP 头确认可用
- [ ] Nginx 429 JSON 格式统一（需配置自定义 error_page）

**结论**: 后端层已基本就绪，建议先完成 `clearIp()` 修正，再进入 Nginx phase。
